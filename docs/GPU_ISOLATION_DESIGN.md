# GPU Isolation — Design Proposal

Status: **Design** (proposal). This document specifies how joblet should expose
NVIDIA GPUs to isolated jobs correctly and safely. It is grounded in how the
NVIDIA Container Toolkit / CDI actually work, and mapped onto joblet's existing
init-side filesystem isolation. It supersedes the aspirational parts of
`GPU_SUPPORT_DESIGN.md`.

> The development host has no GPU. Everything here is validated by unit tests for
> logic and must be validated end-to-end on a GPU host via `09_gpu_test`.

---

## 1. Goals and non-goals

**Goals**
- A job requesting `--gpu=N` can actually run CUDA: open `/dev/nvidia*`, load the
  driver's user-space libraries, and see only the GPUs allocated to it.
- Correct across driver versions (the user-space driver libs must match the
  running kernel module exactly).
- Safe for multi-tenant: no cross-job GPU-memory data leakage, no access to
  unallocated GPUs.
- Fits joblet's model: per-job chroot + mount namespace, unprivileged job user
  (`nobody`/65534), no user namespace, no external daemon required for the common
  case.

**Non-goals (initially)**
- Fine-grained fractional-GPU scheduling beyond whole-GPU and MIG instances.
- vGPU / SR-IOV, GPUDirect RDMA, or multi-node GPU fabrics.
- Non-NVIDIA GPUs (AMD ROCm / Intel) — the architecture leaves room but this doc
  is NVIDIA-specific.

---

## 2. What GPU isolation actually requires

A container/sandbox with a GPU is not just "mount /usr/local/cuda". Four distinct
things must be true inside the job's mount namespace:

1. **Device nodes** exist and are openable:
   - `/dev/nvidiactl` — control device (always).
   - `/dev/nvidia-uvm`, `/dev/nvidia-uvm-tools` — Unified Virtual Memory (always
     for CUDA).
   - `/dev/nvidia<N>` — one char node per allocated GPU (major 195, minor = index).
   - `/dev/nvidia-modeset`, `/dev/dri/card*`, `/dev/dri/renderD*` — **only** for
     graphics/display capability.
   - `/dev/nvidia-caps/nvidia-cap<M>` — **only** for MIG (capability access).
2. **Driver user-space libraries** are present and resolvable by `ld.so`:
   - `libcuda.so.<driver-version>` (the *driver's* CUDA — **not** the CUDA
     toolkit), symlinked as `libcuda.so.1` / `libcuda.so`.
   - `libnvidia-ml.so.<version>` (NVML — what `nvidia-smi` and monitoring use).
   - `libnvidia-ptxjitcompiler.so.<version>`, `libnvidia-nvvm.so.<version>`.
   - GPU firmware `gsp*.bin`, and the `nvidia-smi` binary (optional but expected).
   - `.so.1` → `.so.<version>` symlinks created, and `ldconfig` run so the loader
     finds them.
   > **This is the piece the current code gets wrong**: it bind-mounts the CUDA
   > *toolkit* (`/usr/local/cuda`), which is the application's concern. The thing
   > that must come from the host is the *driver* stack, versioned to the running
   > kernel module. If `libcuda.so.1` doesn't match the loaded driver, CUDA init
   > fails with `CUDA_ERROR_SYSTEM_DRIVER_MISMATCH`.
3. **Device access is confined**: the job can open its allocated GPUs and nothing
   else.
4. **Compute/memory isolation** matches the tenancy model (see §6).

References: NVIDIA Container Toolkit / libnvidia-container, the CDI spec, and the
cgroup-v2 eBPF device controller (see Sources).

## 3. Threat model / security requirements

- **GPU memory is never scrubbed by the driver.** CUDA does not zero memory on
  allocation or free, and the driver does not scrub between contexts/processes.
  A job can read another job's leftover data from GPU DRAM. For multi-tenant this
  is the dominant risk.
  - **Requirement:** on a shared physical GPU, either (a) partition with **MIG**
    (hardware-isolated memory), or (b) allocate **whole GPUs exclusively** and
    **zero GPU memory between jobs**. Never co-schedule untrusted tenants on the
    same non-MIG GPU without scrubbing.
- **Unallocated-GPU access:** a job must not be able to open a GPU it wasn't
  granted. joblet's minimal `/dev` (only the allocated nodes are created) is the
  primary control; a cgroup device rule is defense-in-depth.
- **Privilege:** the job runs as `nobody`. Device nodes are created `0666` so the
  unprivileged job can open them (matching the host's `/dev/nvidia*` perms). No
  setuid path is introduced.
- **Driver/version integrity:** the injected user-space libs must be exactly the
  host's, versioned to the loaded kernel module. Never let a job supply its own
  `libcuda.so`.

## 4. Key decision: build vs. reuse the NVIDIA stack

Injecting the correct driver libraries — discovering them, resolving versions,
creating symlinks, updating the ld cache, handling ARM vs x86, CUDA forward-compat
— is genuinely hard and changes across driver releases. NVIDIA maintains exactly
this logic in **libnvidia-container** (`nvidia-container-cli`) and the **CDI**
specs generated by `nvidia-ctk cdi generate`.

**Recommendation: adopt CDI as the interface, with a native fallback.**

- **Preferred path — CDI/`nvidia-container-cli` (when present):** at job setup,
  consume a CDI spec (or call `nvidia-container-cli configure`) to inject devices
  + driver libs + ldconfig into the job root. This offloads the brittle
  driver-discovery/versioning to NVIDIA's maintained tooling and is the direction
  the whole ecosystem is moving (CDI is the default in recent GPU Operator).
  joblet already builds the job rootfs on the host before pivot, which is exactly
  where `nvidia-container-cli configure --ldconfig=... <rootfs>` operates.
- **Fallback path — native injection:** for hosts without the toolkit, keep a
  minimal native injector (what the current code does) that: creates the compute
  device-node set, discovers the driver libs via `ldconfig -p` / NVML, bind-mounts
  them read-only, creates the `.so` symlinks, and runs `ldconfig` in the job root.
  This covers the compute-only case but is explicitly "best-effort".

Discovery (enumerate GPUs, driver version, per-GPU memory, MIG state) should use
**NVML** via `github.com/NVIDIA/go-nvml` (falling back to parsing `nvidia-smi`),
not ad-hoc probing.

Rationale: joblet's ethos is self-contained, but re-implementing the driver
injection correctly across the driver matrix is a maintenance trap. Treating CDI
as the contract keeps joblet correct where the toolkit is installed, while the
native path keeps a no-dependency story for simple setups.

## 5. Architecture in joblet

The split follows joblet's existing server/init boundary. **Only the init process,
inside the job's mount namespace, can create device nodes and mounts** — the
server cannot (its namespace isn't the job's). This is why the original
server-side `CreateGPUDeviceNodes`/`MountCUDALibraries` were no-ops.

```
┌─ Server (joblet daemon) ────────────────────────────────────────────┐
│ 1. Discovery      NVML/go-nvml: GPUs, driver version, mem, MIG      │
│ 2. Allocation     gpu.Manager: pick GPU(s) or MIG instance(s);      │
│                   memory-based scheduling; mark InUse               │
│ 3. Capability     resolve NVIDIA_DRIVER_CAPABILITIES (default       │
│                   compute,utility)                                  │
│ 4. Forward        emit to init via reserved JOB_GPU_* env:          │
│                     JOB_GPU_INDICES, JOB_GPU_UUIDS (MIG),           │
│                     JOB_GPU_CAPABILITIES, JOB_GPU_CDI_DEVICE,       │
│                     JOB_GPU_DRIVER_LIBS / JOB_GPU_CUDA_MOUNTS       │
└──────────────────────────────┬──────────────────────────────────────┘
                               │ env (JOB_ namespace is reserved from clients)
┌─ Init (PID 1 in job ns) ─────▼──────────────────────────────────────┐
│ filesystem.Setup():                                                 │
│   PRE-chroot  (host paths still visible, mounting into RootDir):    │
│     • CDI path: nvidia-container-cli configure <RootDir>            │
│       OR native: bind-mount driver libs RO, create symlinks         │
│     • run ldconfig against the job root                             │
│   performChroot()                                                   │
│   POST-chroot (absolute /dev paths inside job):                     │
│     • mknod the allocated device-node set (compute ± graphics/MIG)  │
│   drop privileges to nobody, exec job command                       │
└─────────────────────────────────────────────────────────────────────┘
```

joblet is effectively implementing a **minimal, native CDI consumer**: the server
produces the "which GPU + which caps" decision, and init performs the injection.
Where `nvidia-ctk`/`nvidia-container-cli` exists, we delegate injection to it;
otherwise we do the compute-subset natively.

## 6. Component design

### 6.1 Discovery (`internal/joblet/gpu`)
- Use go-nvml: `nvmlDeviceGetCount`, per-device `GetIndex`, `GetUUID`,
  `GetMemoryInfo`, `GetMigMode`, and MIG instance enumeration
  (`GetMaxMigDeviceCount`, `GetMigDeviceHandleByIndex`, `GetGpuInstanceId`).
- Record **driver version** (`nvmlSystemGetDriverVersion`) — used to locate the
  matching user-space libs and to reject jobs if the driver is absent.
- Fallback: parse `nvidia-smi --query-gpu=... --format=csv`.
- Cache discovery at daemon start; refresh on demand (MIG geometry can change).

### 6.2 Allocation model (`gpu.Manager`)
- **Whole GPU:** allocate by index; mark `InUse`; exclusive by default.
- **MIG instance:** allocate a GPU *instance* by UUID; the unit of hardware
  isolation. Preferred for multi-tenant sharing.
- **`--gpu-memory`:** a **scheduling filter only** on non-MIG GPUs (pick a device
  with ≥ requested free memory). It is **not** a runtime cap — there is no cgroup
  for GPU memory. On MIG, memory is bounded by the chosen instance profile
  (e.g. `1g.5gb`). Document this honestly; do not claim enforcement.
- Persist allocations so they survive daemon restart and are released on job end.

### 6.3 Device-node injection (init, post-chroot)
Create only what the capability set requires (isolation-by-omission):
- Always (compute): `/dev/nvidiactl` (195:255), `/dev/nvidia-uvm` (237:0),
  `/dev/nvidia-uvm-tools` (237:1), and `/dev/nvidia<N>` (195:N) per allocated GPU.
- `graphics`/`display`: add `/dev/nvidia-modeset` (195:254) and the relevant
  `/dev/dri/card*` + `/dev/dri/renderD*`.
- MIG: add the `/dev/nvidia-caps/nvidia-cap<M>` nodes for the allocated instance
  (minors come from `/proc/driver/nvidia-caps/mig-minors`).
> **Gap in current code:** it creates `nvidiactl`, `nvidia-uvm`, and `nvidiaN` but
> **omits `nvidia-uvm-tools`** (needed by CUDA) and has no MIG/graphics nodes.

### 6.4 Driver-library injection (init, pre-chroot)
- **CDI/CLI path (preferred):** `nvidia-container-cli --load-kmods configure
  --device=<indices|uuids> --compute --utility --ldconfig=@/sbin/ldconfig
  <RootDir>`. This mounts the versioned driver libs, creates symlinks, and updates
  the ld cache inside the root.
- **Native fallback:** discover the driver libs (from NVML/`ldconfig -p`), bind
  mount them read-only into `<RootDir>/usr/lib/...`, create `libcuda.so.1`→
  `libcuda.so.<ver>` (and peers) symlinks, then run `ldconfig -r <RootDir>`.
- **Never** mount the CUDA *toolkit* as the mechanism — the toolkit belongs to the
  runtime image. (The current `--volume`/runtime image can still ship the toolkit.)

### 6.5 Device-access confinement
- **Primary:** minimal `/dev` — only the allocated nodes exist in the job, so a
  job cannot open a GPU it wasn't granted (there is no host `/dev` bind-mount).
- **Defense-in-depth (optional):** attach a cgroup-v2 device filter. cgroup v2 has
  no `devices` controller; access is mediated by an eBPF `BPF_PROG_TYPE_CGROUP_DEVICE`
  program attached to the job cgroup that allows only the granted (major,minor)
  pairs and denies the rest. **joblet already runs an eBPF stack (cilium/ebpf) for
  telematics**, so this is a natural extension rather than a new dependency. On
  cgroup v1 hosts, write `devices.allow` instead (already partially present).
  > This replaces the current v2 path, which only logs.

### 6.6 Compute/memory isolation & scrubbing
- **MIG (Ampere+):** the only hardware-isolated sharing — dedicated memory slices,
  SMs, L2, fault isolation, memory QoS. Use it for untrusted multi-tenant sharing.
- **Non-MIG shared GPU:** no memory/compute isolation. If joblet allows more than
  one job per physical GPU here, it must **zero GPU memory between jobs** (e.g. a
  short "scrub" step that allocates all free memory and `cudaMemset`s it, or a
  full `nvidia-smi --gpu-reset` when no other context is attached). The current
  `ClearGPUMemory` (best-effort `--gpu-reset` with a no-op fallback) is
  **insufficient** and must not be presented as a guarantee.
- **Default policy:** exclusive whole-GPU allocation (no sharing) unless MIG is
  configured — safe by default.

### 6.7 Capabilities & environment
- Model `NVIDIA_DRIVER_CAPABILITIES` (`compute,utility` default; `graphics`,
  `video`, `display`, `all`). The capability set drives which nodes/libs are
  injected (§6.3/§6.4).
- Env forwarded to the job: `NVIDIA_VISIBLE_DEVICES`, `CUDA_VISIBLE_DEVICES`
  (indices for whole-GPU, MIG UUIDs for MIG), `NVIDIA_DRIVER_CAPABILITIES`, and
  `LD_LIBRARY_PATH`/`PATH` additions for the injected libs.

## 7. Lifecycle

```
submit --gpu=N [--gpu-memory=..] [--gpu-caps=..]
  → validate (count ≥ 0, runtime GPU/CUDA compat)
  → allocate (Manager): pick device(s)/MIG instance; mark InUse; persist
  → forward JOB_GPU_* to init
  → init: (pre-chroot) inject driver libs + ldconfig
          (post-chroot) mknod device nodes
          drop privs, exec
  → job runs
  → on exit: release allocation; (shared non-MIG) scrub GPU memory;
             (MIG, if dynamic) optionally destroy the instance
```

## 8. Config & CLI

- Daemon `gpu:` config: `enabled`, `discovery` (nvml|nvidia-smi),
  `injection` (cdi|native|auto), `allow_shared` (bool),
  `require_mig_for_sharing` (bool), `default_capabilities`.
- Per-job: `--gpu=N` (count), `--gpu-memory=SIZE` (scheduling filter),
  `--gpu-caps=compute,utility,...`. (`--gpu`/`--gpu-memory` already exist and
  parse; add `--gpu-caps`.)

---

## 9. Multi-tenant guidance (doc-facing)

- **Trusted single-tenant:** whole-GPU or best-effort sharing is fine.
- **Untrusted multi-tenant:** require **MIG**, or **exclusive whole-GPU +
  memory-scrub-on-release**. Never share a non-MIG GPU across tenants without
  scrubbing — GPU DRAM is not cleared by the driver.

## 10. Phased roadmap

- **P0 (done / in review):** server→init `JOB_GPU_*` forwarding; init creates the
  compute node set; no-op adapters removed. Unit-tested; **not GPU-validated**.
- **P1 — correctness (partially done):**
  - **Done:** added `/dev/nvidia-uvm-tools`; switched the primary library
    mechanism from the CUDA *toolkit* to native **driver-library** injection —
    `discoverDriverLibraries` finds the versioned driver `.so`s in the standard
    lib dirs, `injectDriverLibraries` bind-mounts them read-only into the job root
    and recreates the SONAME symlinks so the loader resolves `libcuda.so.1` etc.
    Unit-tested (`TestDriverSoname`, `TestDiscoverDriverLibraries`,
    `TestInjectDriverLibraries`); **still not GPU-validated**.
  - **Remaining:** prefer CDI/`nvidia-container-cli` where present (more robust
    SONAME/ldconfig handling than the native heuristic); NVML/go-nvml discovery
    incl. driver version; ldconfig invocation as a belt-and-suspenders to the
    standard-dir placement.
- **P2 — confinement:** cgroup-v2 eBPF device filter (reuse the telematics eBPF
  stack); capability-driven node/lib selection.
- **P3 — sharing safety (partially done):**
  - **Done:** scrub-on-release with a **quarantine** policy (`gpu.scrub_policy:
    strict`) — a GPU whose memory can't be verified clean after reset is excluded
    from allocation instead of handed to another job. This is what makes exclusive
    multi-tenant safe. MIG **allocation model**: MIG instances are discovered
    (`ParseMIGDevices` from `nvidia-smi -L`) and allocated as the unit of
    isolation, and the instance **UUID** is forwarded as CUDA/NVIDIA_VISIBLE_DEVICES
    so CUDA targets the instance. All unit-tested.
  - **Remaining (hardware-gated):** deriving and provisioning the MIG
    `/dev/nvidia-caps/nvidia-cap*` nodes for an instance (needs real MIG hardware
    and `/proc/driver/nvidia-caps/mig-minors`); a real memory-zeroing scrubber
    (CUDA kernel) as an alternative to `--gpu-reset`; honest per-instance
    `--gpu-memory` from the MIG profile.
- **P4 — polish:** MPS opt-in for cooperative sharing; metrics (utilization,
  memory) via NVML; graphics/display capability.

## 11. Testing strategy

- **Unit (no GPU, CI-safe):** env parse/forward; device-node set selection per
  capability (assert the exact mknod calls via the platform fake); driver-lib
  discovery/symlink logic; allocation/scheduling and release; eBPF rule
  construction. *(P0/P1 pieces are already unit-tested this way.)*
- **Simulation mode (no GPU, real server):** `gpu.simulate: true` presents fake
  GPUs (`gpu.SimulatedDiscovery`), so the *entire control plane* runs on a
  GPU-less host — a real `--gpu=N` job flows through allocation → env forwarding →
  init actually `mknod`s `/dev/nvidia*` (works as root without hardware) and
  attempts driver-lib injection. An e2e test can assert those observable outcomes
  (nodes present in the job, `CUDA_VISIBLE_DEVICES` set). It cannot validate that
  CUDA runs — that still needs real hardware (`09_gpu_test`).
- **GPU host e2e (`09_gpu_test`, gated):** a real CUDA job runs; `/dev/nvidia*`
  present and openable as `nobody`; `nvidia-smi` and a `cudaMalloc` sample succeed;
  a job sees only its allocated GPU(s); (multi-tenant) no cross-job memory
  readback after scrub; MIG instance isolation. **Nothing merges as "working" on
  unit tests alone — the gated suite must pass on hardware.**

## 12. Gaps vs. the current implementation

| Area | Current | This design |
|---|---|---|
| Where injection runs | init (fixed this session) | init ✓ |
| Library injection | bind-mounts CUDA *toolkit* | inject *driver* libs via CDI/CLI (native fallback) + ldconfig |
| Device nodes | ctl/uvm/nvidiaN | + `nvidia-uvm-tools`, graphics & MIG nodes, capability-driven |
| Discovery | path probing / basic | NVML (go-nvml) incl. driver version + MIG |
| Confinement | v1 rules; v2 logs only | v2 eBPF device filter (reuse telematics stack) |
| Memory limit | claimed, not enforced | scheduling filter (non-MIG) / MIG profile; documented honestly |
| Multi-tenant scrub | best-effort `--gpu-reset` | MIG or exclusive + mandatory scrub-on-release |
